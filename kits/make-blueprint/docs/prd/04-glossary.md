# 04 Glossary

## Purpose

This glossary defines the words used across the Make Blueprint PRD set, so people and agents read each term the same way. Each term has one definition, written to match how its owning PRD uses it, and a link to that PRD. When a definition here and the owning PRD differ, the owning PRD wins and the difference goes into [03 Open Questions and Risk Register](03-open-questions-and-risk-register.md).

The list is in alphabetical order, ignoring code formatting and letter case. Terms in code formatting are exact values, field names or commands.

Two terms are easy to confuse. A Persona, with a capital P, is an audience role for this product: a `user` or `maintainer` entry in the shared people and roles file, `.make/personas.yaml`. A persona record is a record of type `persona` that describes a role in a client's systems. The two are related: each persona record points to its `user` entry in that file by slug, so a client role can also be an audience for the project's docs. Sentences say "persona record" for the Make Blueprint record type and "Persona" for the audience role.

## Terms

| Term | Definition | Notes |
| --- | --- | --- |
| `active` | A record status: reviewed and in use, so the record is a trusted fact. The model, compare, place and hand-off stages work from `active` records. Exports hold the records that pass the status filter, which is `active` by default. | Owner: [10 Records and Identity](10-records-and-identity.md). Review makes drafts `active` in [13 Extraction and Review](13-extraction-and-review.md). Status filter: [15 Exports](15-exports.md). |
| Agent conversion | Converted text that an agent writes for a complex PDF through the agent route. The route is allowed only for a PDF, and only when the built-in converter reports a trouble signal (a table, a scanned page with no text layer or a complex layout) or a person asks for it. The CLI hands out page batches, and the agent writes Markdown for prose and CSV for tables, with one CSV file for each level of a nested table. The CLI adds the anchors, confirms that every page is covered, and compares numbers and words against the PDF's text layer where it has one. The source record names the converter as `agent`, with `converter_model` and `converted_at`. A person reviews the text, with flagged and "unchecked" pages first, before the source counts as `converted`. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). Skill: [16 Workflow and Skills](16-workflow-and-skills.md). Review: [13 Extraction and Review](13-extraction-and-review.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| Agent tool | The program that runs an agent session, also called a harness. It keeps skill folders and MCP config and starts the Make Blueprint MCP server. v2.0 supports Claude Code, Codex and GitHub Copilot CLI. | Owner: [07 Installation and Distribution](07-installation-and-distribution.md). |
| Alias | Another name that still finds a record, kept in `aliases`: a former `ref` after a ref fix, or an imported name such as a v1 `REF-NNN` or a system slug. Aliases are kept for good, and a new `ref` never reuses their numbers. Every command that takes a record name accepts an alias. | Owner: [10 Records and Identity](10-records-and-identity.md). Imported aliases: [17 v1 Import](17-v1-import.md). |
| `allowWrite` | The argument that an MCP write tool needs on each call before it changes anything. It covers only the call that carries it. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). |
| Anchor | A kind code, a hyphen and a number of at least three digits that names one element of a converted text: `h` for a heading, `p` for a paragraph, `r` for a row of a table that stays in the Markdown file and `t` for an extracted table, as in `p-012` or `t-001`. Each kind is numbered on its own in reading order. The marker is `<a id="p-012"></a>` at the start of each element. Make Blueprint uses the marker only in its converted text, and Make Docs docs never use it. The same original bytes and converter version always give the same anchors. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). |
| Approval batch | One part of a large approval: a set of records small enough to write under one short hold of the write lock. Each batch is its own journaled change and lands whole or not at all. A large approval that stops between batches reports `partial` and can be run again. | Owners: [09 Storage and Indexing](09-storage-and-indexing.md) for batches and the journal, [13 Extraction and Review](13-extraction-and-review.md) for the order of approval. |
| `archived` | A record status: no longer in use, with no replacement. The record stays for history. It is an end state in v2.0. | Owner: [10 Records and Identity](10-records-and-identity.md). |
| `audience` | A field on capability and requirement records: a list of `user` slugs from `.make/personas.yaml` that names the user roles the record serves. It holds slugs, not record `id` values. | Owner: [11 Record Types Reference](11-record-types-reference.md). Slug checks: [10 Records and Identity](10-records-and-identity.md). |
| Baseline system | A system whose capabilities the target system must cover in a comparison. A comparison has one or more baseline systems. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Block hash | A hash of a managed block's text, kept in the machine Store, that shows whether someone edited the block since the tool last wrote it. | Owner: [06 Project Layout and Instruction Files](06-project-layout-and-instruction-files.md). |
| `blocked` | Three uses of one word. A command outcome: the command could not run and changed nothing, and it names what to do. A part outcome in an extraction: the part could not be worked. An `extraction_status` value: the source's latest extraction finished blocked. | Owners: [08 CLI and MCP](08-cli-and-mcp.md) for the command outcome, [13 Extraction and Review](13-extraction-and-review.md) for the other two. |
| `blueprint-convert` | The skill that guides the agent route for complex PDFs: when the route is allowed, how to work through page batches, how to keep meaning, links and footnotes, how to lay out nested tables, and how to hand the pages to review. It is not a stage of its own. It serves the intake stage and uses the `intake` profile. | Owner: [16 Workflow and Skills](16-workflow-and-skills.md). Route: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). |
| `blueprint-report` | The skill that drafts the prose that exports show into records, with a checklist that matches the export layout, and runs the exports. It is not a stage of its own. It serves the model, compare and place stages. | Owner: [16 Workflow and Skills](16-workflow-and-skills.md). Exports: [15 Exports](15-exports.md). |
| `blueprint/sources/.gitignore` | The managed git ignore file that Make Blueprint writes and owns. It lists exactly the source files that their git level keeps out of git, and `run source add` lists each new one in the same change that registers it. Make Blueprint writes git rules only inside `blueprint/sources/`. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). Layout: [06 Project Layout and Instruction Files](06-project-layout-and-instruction-files.md). |
| `build` | A delivery value: the owning system gets a capability it does not have today. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Candidate matches | The target capabilities that `run compare next` returns with each baseline capability. The index text search finds them with the same matching rule as duplicate hints, and lists target capabilities in the same domain first. They are hints only, and the agent may cite any target capability. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Search: [09 Storage and Indexing](09-storage-and-indexing.md). |
| `capability` | A record type, prefix `CAP`: one capability of one system. It stores its `system`, an optional `parent` capability, its `domain` and its `capability_status`, and optional detail fields such as `capability_type`, `triggers`, `outcomes`, `entities`, `depends_on` and `audience`. | Owner: [11 Record Types Reference](11-record-types-reference.md). Used in [13 Extraction and Review](13-extraction-and-review.md) and [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Capability model document | `<system-ref>-capability-model.md`, the narrative export for one system, which a client reads first. It holds an about part, one numbered part for each domain, one numbered section for each capability with its requirements and fit-gap results, an integrations part, a capability inventory, and findings and source notes. | Owner: [15 Exports](15-exports.md). |
| Capability status | The `capability_status` of a capability: a value from its system's own status list (`capability_statuses`) that says how far the capability has come in that system. It is not a record status and not a verdict. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Field: [11 Record Types Reference](11-record-types-reference.md). |
| Checkout | One working folder of a project, such as a clone or a git worktree. Each checkout has its own derived index, write lock and write journal. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). |
| `comparison` | A record type, prefix `CMP`: one target system compared with one or more baseline systems, named in `target_system` and `baseline_systems`. Its fit-gap records hold the scores. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| Confidence | How well the evidence supports a fit-gap verdict: `high` (the evidence states the fit directly), `medium` (part rests on inference) or `low` (a working assumption that needs confirming). | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| `configurable` | A fit-gap verdict: the target meets the baseline capability through settings, parameters or setup data, with no code. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| `configure` | A delivery value: the owning system meets the capability through settings and setup data, with no code. A `native` fit also uses `configure`, with little or nothing to set. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Conflict copy | Make Blueprint's planned block, saved in `.make/blueprint/conflicts/` for review when a person chooses to keep their edited block. | Owner: [06 Project Layout and Instruction Files](06-project-layout-and-instruction-files.md). |
| Connection ID and key | Two values in each MCP server entry that identify one reviewed agent-tool connection. The machine Store keeps only a hash of the key. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). |
| Content version | A hash of the fields that carry the meaning of a requirement or capability. It is the SHA-256 hash, with LF line endings, of a fixed serialization of a requirement's `title`, `summary`, `kind`, `option_values`, `option_default`, `option_scope` and Markdown body, or of a capability's `title`, `summary` and body, written as 64 lowercase hexadecimal characters. Tags, facets, `owners`, `stakeholders`, `audience`, links, evidence, timestamps and `schema_version` do not change it. A requirement mark keeps it in `version`, so only a change of meaning makes the mark out of date. It is not the record version, which guards writes. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). Marks: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Field: [11 Record Types Reference](11-record-types-reference.md). |
| Conversion status | The `conversion_status` of a source: `converted`, `needs-manual` (no built-in converter, so text must be supplied), `failed` (the converter could not read the file), `agent-in-progress` (page batches of an agent conversion are out) or `awaiting-review` (every page of an agent conversion is written, and the text waits for review). `converted` means the converted text matches the recorded hash and converter version. Agent text, once review approves it, needs only the original's hash to match, so a new model or CLI version never makes it stale. Extraction waits until a source is `converted`. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). Review: [13 Extraction and Review](13-extraction-and-review.md). |
| Converted text | Markdown made from an original file, with one anchor for each heading, paragraph and row, stored next to the original with `.md` after its name, as in `pricing.xlsx.md`, plus one table CSV file for each extracted table. Its front matter names the source `id`, hash, converter and parts. A built-in converter writes it, an agent or person supplies it, an agent writes it through the agent route with `converter: agent`, or the v1 import keeps it with `converter: v1`. It is never edited by hand. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). |
| Converted twin | A v1 converted text file with YAML front matter, kept in the v1 `assets/<source-slug>/` folder. The v1 import keeps it as the source's converted text, with `converter: v1`. | Owner: [17 v1 Import](17-v1-import.md). |
| Core release | A published version of the shared core package, `@brucewaynedecoy/make-core`, built from `packages/core/` in the make-kit monorepo. A core change ships in a core release before a Make Blueprint release can use it, and each Make Blueprint release pins one exact core version. | Owner: [05 Ecosystem and Shared Core](05-ecosystem-and-shared-core.md). |
| Coverage | How much of one part of a source an extraction read: `none`, `partial` or `full`. A part with `partial` coverage brings the source back through `run extract next`. | Owner: [13 Extraction and Review](13-extraction-and-review.md). |
| Coverage read | One read, through `run compare show`, of what is left to score, place and hand off in one comparison. It also lists fit-gap records with out-of-date marks, and current integrations that touch a baseline system and that no planned integration replaces. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Integrations: [19 System Integrations](19-system-integrations.md). |
| Covering capabilities | The target capabilities that cover one baseline capability on a fit-gap record, kept in `covering_capabilities`. A `gap` has none; a `target-only` record has exactly one. Every target capability that a requirement mark names is one of them, and `project check` reports a mark that names any other as `mark-capability-uncovered`. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Check code: [10 Records and Identity](10-records-and-identity.md). |
| Current record | A record whose status is `draft` or `active`. Rules about uniqueness, duplicates, links, coverage and exports count only current records. | Owner: [10 Records and Identity](10-records-and-identity.md). Also used in [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Data dictionary export | A Markdown export that explains a set of CSV files, so a reader can use them without help. `<system-ref>-data-dictionary.md` covers one system's files, and `<comparison-ref>-data-dictionary.md` covers one comparison's files. It lists the files, the model shape, every column, every value list with its counts, the join rules and encoding notes. | Owner: [15 Exports](15-exports.md). |
| Database backend | The storage backend that setup C uses to reach a shared database, behind the same storage interface. It is planned for v3 and not yet designed. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). |
| Deferred obligation | A tracked promise to end a temporary workaround when a named future event happens, with an owner and exit criteria. O-001 is Make Blueprint's one obligation: `project check` skips Make Docs links until Make Docs ships its read command. | Owner: [03 Open Questions and Risk Register](03-open-questions-and-risk-register.md#o-001-confirm-make-docs-links-in-project-check). |
| Delivery | How the owning system provides a placed capability: `configure`, `extend`, `build` or `integrate`, stored in a placement's `delivery`. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Derived index | The SQLite index, built with `node:sqlite` from the record files, that answers filters, SQL, text search, status and checks. Each checkout has its own index file in the machine Store, and git never tracks it. Deleting it loses nothing, because it is rebuilt. Also called the local index. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). |
| `domain` | A record type, prefix `DOM`: one entry in the project's shared domain list, with a `code` and a `name`. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| `draft` | A record status: created but not reviewed, so not yet a trusted fact. Every record that extraction creates starts here, and so do the records that compare and place create. | Owner: [10 Records and Identity](10-records-and-identity.md). Review: [13 Extraction and Review](13-extraction-and-review.md). |
| Dry run | A run that shows what a command would do and writes nothing. The v1 import always shows a dry-run report before it writes. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). Import report: [17 v1 Import](17-v1-import.md). |
| Due source | A ready source, converted and with its converted text on this machine, that has never been extracted, was partly extracted, or changed since its latest extraction. `run extract next` hands out due sources in that order. | Owner: [13 Extraction and Review](13-extraction-and-review.md). |
| Duplicate hint | A likely matching record that the CLI shows before a new record is created, through `run extract add` or `run record create`, so the agent can link to it instead of making a duplicate. | Owner: [13 Extraction and Review](13-extraction-and-review.md). |
| Effort | The size of the work needed to deliver the baseline outcome with the target system: `none`, `low`, `medium`, `high` or `unknown`. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Evidence link | A pointer from a record to an exact place in a source: the source record's `id`, a `#` and an anchor, as in `SRC-4hd8x7k2#p-012`, or a table position, as in `SRC-4hd8x7k2#t-001:r-0012:c-003`. A record keeps its links in `evidence`. Every fit-gap record needs at least one. | Owner: [10 Records and Identity](10-records-and-identity.md) for the format and validation; [12 Source Intake and Conversion](12-source-intake-and-conversion.md) for anchors, table positions and following a link. |
| `evidence_versions` | A record field that holds, for each source its evidence links name, that source's `sha256`, `converter` and `converter_version` when the links were made or last confirmed. A difference from the source's current version shows the link as `old-version`. | Owner: [10 Records and Identity](10-records-and-identity.md). |
| Export | A generated file in `blueprint/exports/` that a client opens without Make Blueprint: a CSV file, a Markdown document or the xlsx workbook of a comparison. The CLI builds every export, prose included, from the records that pass the status filter and the export format version alone. Exports are never the truth, a command makes them again at any time, and nothing reads them back. | Owner: [15 Exports](15-exports.md). |
| Export check | A check in every export run that confirms each `id`, section number and count in the built files matches the records, before any file is written. A failed check fails the run, names the file and the value, and leaves the previous files in place. | Owner: [15 Exports](15-exports.md). |
| Export format version | The version that names the layout of every export file. It ships with Make Blueprint, so the same records and the same export format version always give byte-identical files. Each data dictionary names it. | Owner: [15 Exports](15-exports.md). |
| `extend` | A delivery value: code, extensions or customization go on top of a capability the owning system already has. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| `extraction` | A record type, prefix `EXT`: one pass over one source at one version of its original. It records who ran it (`extracted_by`), the coverage, outcome and note for every part, and the records it created or updated. | Owner: [13 Extraction and Review](13-extraction-and-review.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| Extraction status | The `extraction_status` of a source: `not-started`, `in-progress`, `extracted` or `blocked`. "Partly extracted" and "changed since extraction" are worked out, not stored. | Owner: [13 Extraction and Review](13-extraction-and-review.md). Field: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). |
| Facet | A named value list that a project defines in its config, such as legal entity, release or scope. Any record can carry codes from it in `facets`. Facets, not custom record types, are how a project extends records. | Owner: [10 Records and Identity](10-records-and-identity.md). |
| File backend | The v2.0 storage backend: each record is one Markdown file at `blueprint/records/<type>/<id>.md`, written so each change is a small git diff. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). |
| Filter syntax | The one short expression language that selects records by type, field, facet, status and link. The CLI takes it in `--filter` and MCP tools take it in a `filter` argument. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). The index behind it: [09 Storage and Indexing](09-storage-and-indexing.md). |
| `finding` | A record type, prefix `FIND`: something found in sources or analysis, with `kind` set to `gap`, `risk`, `question` or `observation`. Open questions in a source become findings of kind `question`. | Owner: [11 Record Types Reference](11-record-types-reference.md). Used in [13 Extraction and Review](13-extraction-and-review.md). |
| `fit-gap` | A record type, prefix `FIT`, also called a fit-gap record: one baseline capability scored against the whole target system in one comparison, with a verdict, confidence, effort, `gap_detail`, `migration_note`, covering capabilities, requirement marks and at least one evidence link. The grain is the capability, and the marks back the verdict. A `target-only` record has no marks. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| Fit-gap method | The fixed steps that the CLI controls and the compare skill follows. `run compare next` hands out one baseline capability at a time. The agent marks each requirement with evidence, the verdict follows from the marks by the verdict table, and the rubric guides confidence and effort. The compare commands refuse a draft that lacks a field its verdict requires, and a target-only pass follows the baseline pass. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Skill: [16 Workflow and Skills](16-workflow-and-skills.md). |
| `gap` | A fit-gap verdict: no target capability covers the baseline capability. It is also one `kind` of finding record. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md) for the verdict; [11 Record Types Reference](11-record-types-reference.md) for the finding kind. |
| Gap list | For one fit-gap record, the baseline requirements whose mark is `partly`, `unreleased` or `not-met`. The fit-gap detail export lists their refs, and the capability model document lists each one with its mark and note. | Owner: [15 Exports](15-exports.md). Marks: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). |
| Git LFS | A git add-on for large files. Originals of 50 MB or more that git tracks use it by default, with rules in the managed `blueprint/sources/.gitattributes`. A project can change the limit in `sources.lfs_threshold_mb`. | Owner: [12 Source Intake and Conversion](12-source-intake-and-conversion.md). |
| Hand off | The seventh workflow stage: linking placements, and the integration records that deliver them, to Make Docs work items and doc paths. Make Blueprint only links; Make Docs creates and changes work items. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Skill: [16 Workflow and Skills](16-workflow-and-skills.md). Links: [05 Ecosystem and Shared Core](05-ecosystem-and-shared-core.md). Integration records: [19 System Integrations](19-system-integrations.md). |
| Handoff line | One line in a tool's root block that names what the other ecosystem tool owns. A root block carries it only while the other tool is present in the project. When a tool is set up or removed later, it asks the other tool, through the core, to refresh only that tool's own root block. | Owner: [05 Ecosystem and Shared Core](05-ecosystem-and-shared-core.md). Block mechanics: [06 Project Layout and Instruction Files](06-project-layout-and-instruction-files.md). |
| Human output and machine output | The two forms of one command result. Human output is short text for a person at a terminal. Machine output is the full result as JSON, which the MCP server also returns. Both carry the same meaning. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). |
| `id` | The permanent ID of a record: the type prefix, a hyphen and a random part of 8 lowercase letters and digits with at least one letter, as in `REQ-7kq2m7k2`. It never changes. It names the record file, and every relation field and evidence link uses it. | Owner: [10 Records and Identity](10-records-and-identity.md). Prefixes: [11 Record Types Reference](11-record-types-reference.md). |
| Import follow-up | An imported item that a person still has to finish, such as a field v1 never held. The import report lists it, and `project check` finds it after the write. | Owner: [17 v1 Import](17-v1-import.md). |
| In-memory backend | A second, simple storage backend used only in tests, to keep the storage interface free of file-backend details. | Owner: [09 Storage and Indexing](09-storage-and-indexing.md). |
| `integrate` | A delivery value: the owning system provides the capability to the other systems in scope through an integration. The placement lists the integration records that deliver it in `integrations`. | Owner: [14 Fit-Gap and Placement](14-fit-gap-and-placement.md). Integration records: [19 System Integrations](19-system-integrations.md). |
| `integration` | A record type, prefix `INT`: one flow of data or events from one system to another, in one direction, from `from_system` to `to_system`. A two-way exchange is two records. Current integrations come from extraction with evidence, and planned integrations come from analysis as drafts. | Owner: [19 System Integrations](19-system-integrations.md). Fields: [11 Record Types Reference](11-record-types-reference.md). |
| Integration `state` | The `state` of an integration record: `current` for a flow that runs today, or `planned` for a flow that the planned state needs. It is not a record status. | Owner: [19 System Integrations](19-system-integrations.md). Field: [11 Record Types Reference](11-record-types-reference.md). |
| Lifecycle command | A command outside the operation catalog: `setup`, `setup remove`, `update`, `uninstall` and `mcp`, and the `serve` command in v2.1. | Owner: [08 CLI and MCP](08-cli-and-mcp.md). Behavior: [07 Installation and Distribution](07-installation-and-distribution.md). |
| Link state | The result of checking one evidence link: `ok`, `malformed`, `unknown-source`, `unavailable`, `no-anchor`, `not-converted`, `broken`, `old-version` or `unconfirmed`. A link can have more than one state. | Owner: [10 Records and Identity](10-records-and-identity.md). |
| List the project can extend | A built-in list of codes that a project may add its own codes to: the values of `capability_type`, `option_scope` and integration `method`. 11 lists the built-in codes. A project adds its own codes in the settings `lists.capability_type`, `lists.option_scope` and `lists.integration_method` in `.make/blueprint/config.yaml`. Codes use lowercase letters, digits, hyphens and underscores. | Owner: [11 Record Types Reference](11-record-types-reference.md) for the built-in codes. Settings: [06 Project Layout and Instruction Files](06-project-layout-and-instruction-files.md). |
| Local link | Resolving the core through the npm workspace link to `packages/core/` in the make-kit monorepo instead of the published package. Also called the workspace link. Development builds may use it; release builds fail on it. | Owner: [05 Ecosystem and Shared Core](05-ecosystem-and-shared-core.md). |
| Local server | The v2.1 server for setup B. It binds only to the user's own machine, needs no login, serves the Svelte web app and writes no record files in its first version.
