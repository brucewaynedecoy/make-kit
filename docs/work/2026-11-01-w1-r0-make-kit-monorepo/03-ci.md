# Phase 3: CI

## Purpose

This phase gives the repository its Make Docs CI workflow, its one shared publish workflow and the install check that the release gate needs. It is step 5 of the Step 0 sequence ([Q-021](../../prd/03-open-questions-and-risk-register.md#q-021-step-0-sequence)). [Phase 5](05-switch-point.md) uses these workflows for the first release from this repository.

The phase depends on [Phase 2](02-go-public.md), because CI minutes for macOS and Windows and the rulesets need the public repository ([Q-004](../../prd/03-open-questions-and-risk-register.md#q-004-public-repository-before-the-switch)).

## Overview

GitHub reads workflows only at the git root. So the phase builds `.github/workflows/make-docs-ci.yml` from the copied `platform-safety.yml`, and one shared `.github/workflows/publish-npm.yml` from the copied publish workflow. Release tags name the package, and release-candidate digests live in `.github/release-candidates/<tag>.sha256` ([Q-010](../../prd/03-open-questions-and-risk-register.md#q-010-ci-layout-and-release-tags)). The phase also adds the install check of the release gate, because CI installs each release candidate from npm on Linux, macOS and Windows ([08 Build and Release, Release Gate](../../prd/08-build-and-release.md#release-gate)).

After the root workflows exist, the phase removes the copied `kits/make-docs/.github/` folder and rewrites `kits/make-docs/RELEASING.md` for this repository. Nothing is published in this phase.

[Q-034](../../prd/03-open-questions-and-risk-register.md#q-034-ci-for-the-core-and-the-setup-tool) is open. It does not block this phase: `make-docs-ci.yml` runs on changes under `packages/core/` as [08 Build and Release, CI](../../prd/08-build-and-release.md#ci) requires. Q-034 must close before the CI work in [Phase 7](07-shared-core.md).

Owner gates in this phase: none. No task publishes to npm, changes a dist-tag or the trusted publisher, or changes a GitHub repository setting or ruleset.

## Human Experience Outcome

- Impact and governing promise or preserved boundary: `indirect`. Two promises depend on this phase: "A Make Docs user sees no change to the npm package name or the install commands after the switch point" and "A Make Docs user who installs from `latest` gets no version from the new release path until that path has passed on the `next` dist-tag" ([08 Build and Release, Switch Point](../../prd/08-build-and-release.md#switch-point), [08 Build and Release, Release Gate](../../prd/08-build-and-release.md#release-gate)). This phase builds the dry run, the digest check, the dist-tag choice and the install check that Phase 5 uses to keep them. The [Human Experience Contract](make-docs://system/contract/human-experience-contract.md) is the standard behind both.
- Intended human outcome: no change for Make Docs users in this phase. A maintainer who opens a pull request under `kits/make-docs/` sees one result check that passes or fails for Linux, macOS and Windows.
- Human-facing surface or indirect effect: the pull request checks, and later the npm dist-tags that the publish workflow sets.
- Implementation work: Stage 1 builds `make-docs-ci.yml`. Stage 2 builds `publish-npm.yml`, its tag checks and the install check. Stage 3 removes the copied workflows and rewrites `RELEASING.md`.
- Evidence source or testing type selected under current authority: Automated Implementation Testing: a pull request run of `make-docs-ci.yml` on the three operating systems, fixture tests of the publish tag checks, and one install-check run on the published 2.0.6.
- Executor: the implementing coding agent. GitHub Actions runs the checks.
- Accepted obligation or deferral route: none.

## Stage 1 - Make Docs CI Workflow

### Tasks

- [ ] t1: Write `.github/workflows/make-docs-ci.yml` from `kits/make-docs/.github/workflows/platform-safety.yml`. It runs on `pull_request` when a change touches a file under `kits/make-docs/` or `packages/core/`, or the root `package-lock.json`, and on `workflow_dispatch`. Its default permission is `contents: read`, and every job uses Node 24 ([08 Build and Release, CI](../../prd/08-build-and-release.md#ci), [08 Build and Release, Build in the Root Workspace](../../prd/08-build-and-release.md#build-in-the-root-workspace), [Q-010](../../prd/03-open-questions-and-risk-register.md#q-010-ci-layout-and-release-tags)).
- [ ] t2: Put the `kits/make-docs/` prefix on each `v2.0.6` path that needs it: the diff path list, `packages/cli/tsconfig.json`, the package proof script and `packages/cli/package.json`. Change each workspace argument, such as `-w packages/cli`, to the root workspace path `kits/make-docs/packages/cli` ([08 Build and Release, Rebuild Notes](../../prd/08-build-and-release.md#rebuild-notes)).
- [ ] t3: Keep the `v2.0.6` jobs: the platform tests on `ubuntu-latest`, `macos-latest` and `windows-latest`, with `--no-file-parallelism --maxWorkers=1` on Windows; one package candidate built on Ubuntu with the package proof; the install of that tarball on the three operating systems; the compare of the results; and one result job that always runs, so a path filter never leaves a required check waiting ([08 Build and Release, CI](../../prd/08-build-and-release.md#ci)).
- [ ] t4: Make the CI package check read the same digest file as the publish workflow: `.github/release-candidates/make-docs-v<version>.sha256` ([08 Build and Release, Release-Candidate Digests](../../prd/08-build-and-release.md#release-candidate-digests)).
- [ ] t5: Add `npm publish --dry-run` for `@brucewaynedecoy/make-docs` to the pull request run. This is step 1 of the release gate ([08 Build and Release, Release Gate](../../prd/08-build-and-release.md#release-gate)).
  - After `make-docs-ci.yml` runs on pull requests, let it run on each open Dependabot pull request, for example with the comment `@dependabot rebase`. Then merge each one that passes, or close it ([Q-041](../../prd/03-open-questions-and-risk-register.md#q-041-dependabot-pull-requests-before-the-public-step)).

### Acceptance criteria

- A301: On a pull request that changes a file under `kits/make-docs/`, `make-docs-ci.yml` passes its test jobs on `ubuntu-latest`, `macos-latest` and `windows-latest`, its package jobs and its result job.
- A302: On a pull request that changes only a file under `docs/`, the package jobs of `make-docs-ci.yml` do not run, and no check stays pending.
- A303: A script reads every path in `.github/workflows/*.yml` and finds each one in the repository. Each workflow file sets `contents: read` as its default permission.
- A304: The pull request log shows `npm publish --dry-run` for `@brucewaynedecoy/make-docs` with exit 0.

## Stage 2 - Shared Publish Workflow and Install Check

### Tasks

- [ ] t6: Write `.github/workflows/publish-npm.yml` from the copied publish workflow. A published GitHub Release with a release tag starts it. The tag prefix selects the package folder from [08 Build and Release, Release Tags and Packages](../../prd/08-build-and-release.md#release-tags-and-packages). The workflow refuses a tag with an unknown prefix, and a tag whose version differs from the `version` field of the selected package ([Q-010](../../prd/03-open-questions-and-risk-register.md#q-010-ci-layout-and-release-tags)).
- [ ] t7: Keep every `v2.0.6` check for the selected package: the tag is on `origin/main`, the package name matches the tag prefix, the prerelease flag matches the version, the version is not on npm yet, the tarball holds `LICENSE`, and the tarball matches `.github/release-candidates/<tag>.sha256`. A tag with a prerelease part stages on `next`. A tag with no prerelease part stages on `latest`. The workflow pins npm 11.17.0 and runs `npm stage publish "$TARBALL" --access public --tag "$DIST_TAG" --provenance` ([08 Build and Release, Publish](../../prd/08-build-and-release.md#publish)).
- [ ] t8: Give only the publish job `id-token: write`. Keep `contents: read` as the default permission. Use no npm token in any workflow, and add no npm token as a repository secret ([08 Build and Release, Publish](../../prd/08-build-and-release.md#publish)).
- [ ] t9: Put the tag and version checks in one script that the publish workflow calls, and test it in the pull request with fixtures: `make-docs-v2.0.7-rc.0` selects `kits/make-docs/packages/cli/` and `next`; `make-docs-v2.0.7` selects `latest`; `make-core-v0.1.0` selects `packages/core/`; `other-v1.0.0` is refused; and a tag whose version differs from the package version is refused.
- [ ] t10: Write the install check of the release gate as a workflow that `workflow_dispatch` starts with the package name and the version as inputs, for example `.github/workflows/install-check.yml`. On `ubuntu-latest`, `macos-latest` and `windows-latest`, it installs the package from the npm registry, not from a local tarball. For a CLI package it checks that `<cli> --version` prints the input version and sets up a temporary project. For the core, which has no CLI, it installs the package into a temporary project and loads the package entry point ([08 Build and Release, Release Gate](../../prd/08-build-and-release.md#release-gate), [Q-032](../../prd/03-open-questions-and-risk-register.md#q-032-release-gate-scope)).
- [ ] t11: After the pull request merges, run the install check once for `@brucewaynedecoy/make-docs` at version `2.0.6`. This proves the check with no publish.
